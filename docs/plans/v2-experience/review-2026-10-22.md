# V2 implementation plan clarity and contradiction review

Reviewed: 2026-10-22. Basis: current working-tree documents, including uncommitted decisions.

The core journey has a clear scope, but the implementation map has not caught up with the accepted wire and newer experience requirements. Several contract details also need reconciliation before independently implemented clients and servers can interoperate reliably. This is a review of the planned implementation, not a firmware qualification or an implementation authorization.

The findings below preserve the recorded owner decisions. Suggested corrections are proposals, not amendments to those decisions. The implementation map and source specifications were not changed by this review.

## Resolution (2026-10-22, after this review)

The suggested corrections were applied as engineering contract completions. Owner decisions listed at the end of this review were not reopened. Current revisions: login 0.13, envelope 0.10, inbox 0.8, delivery 0.11, profile 0.9, sketch experience 6. The implementation map now assigns the newer requirement IDs and leaves P1 as fixture delivery. The storage medium for a finished send remains an open engineering choice. The byte budget is the accepted 5,760,000-byte PCM capture plus that send’s sketch.

## Findings

### R1 — High: newer acceptance requirements have no package or verifier coverage

**Evidence:** [Implementation map, acceptance traceability and package briefs](implementation.md#acceptance-criteria-traceability), especially lines 55–65, 205–208, and 244–271. Compare [login requirements](../../product/experiences/endpoint-login.md#requirements), lines 364–366; [carousel requirements](../../product/experiences/message-carousel-and-playback.md), lines 744–753; and [send requirements](../../product/experiences/message-recording-and-sending.md), lines 826–841.

The map stops at login `EXP-052`, carousel `EXP-043`, and send `EXP-043`. It omits:

- Login `EXP-053`–`EXP-055`: background refresh, catalog fallback, and the credential expiry bound after a lost invalidate.
- Carousel `EXP-044`–`EXP-045`: refresh-failure presentation and catalog fallback.
- Send `EXP-044`–`EXP-046`: refresh-failure wait, recipient fallback, and suspension of inbox fetching through recording and pending send.

P5 describes issuance and invalidation, but does not deliver the refresh scheduler. P6 and P8 do not own the new inbox-fetch arbitration. An implementer could satisfy the package briefs and still omit these accepted behaviors. P10 still names an “inbox hint during playback,” although the accepted journey has no push channel.

**Suggested correction:** assign session refresh and lifetime handling to P5; roster fallback to P4; inbox fallback, polling, and prefix playback to P6; recipient fallback and outgoing-work priority to P8, with a capture-state interface from P7. Give P10 explicit composed tests for refresh during recording/Volume, pending-send inbox suppression after BOOT, and a polled snapshot during playback. Add the newer requirement IDs to both implementer and verifier coverage. Separate a simulated background event from a product push transport.

### R2 — High: send success bodies are both contradictory and incomplete

**Evidence:** [Shared envelope, schema-version rule](../../product/communication-contracts/user-scoped-envelope.md#proposed-transport-and-authority), line 20; [delivery create, part, and lookup responses](../../product/communication-contracts/message-delivery.md#4-proposed-v2-schemas), lines 92–96 and 135–141.

The envelope requires a schema literal in every JSON success body, with an explicit exception for session refresh. Part upload requires HTTP 200 `{}`, which is another JSON success body but is not listed as an exception. A client following the envelope could reject every successful part acknowledgement.

Create's `open` response has no complete schema or field table. Subsequent routes require a server `message_id`, but its return field for a newly opened upload is not specified. Lookup says `open` resumes missing parts without defining how the response identifies those parts. The accepted receipt shape only covers the terminal `accepted` state.

**Suggested correction:** explicitly exempt the accepted empty part acknowledgement or define a versioned acknowledgement consistently in both contracts. Specify complete create/open and lookup/open bodies, including the upload/message identifier and resumable part state, or explicitly require replaying all parts with idempotent acknowledgements. Add client/server conformance examples for every successful response variant. These are engineering contract completions, not new screen behavior.

### R3 — High: receipt deletion leaves the no-duplicate guarantee without a recovery rule

**Evidence:** [Delivery receipt lookup](../../product/communication-contracts/message-delivery.md#44-receipt-lookup--get-v2outgoingby-client-idclient_message_id-accepted-route), lines 135–149; delivery timing section says there is no product stuck-send deadline.

The contract permits receipt lookup to return `not_found` once the message has disappeared from every recipient inbox. It also instructs a client holding finished work to create/resume the same ID after `not_found`. Yet `COM-002` requires that ID to replay one result and never produce another delivery.

Concrete sequence: complete commits; its response is lost; the sender remains offline; recipients remove the message; the receipt expires; the sender resumes its retained queue. Without retained deduplication evidence, the server cannot distinguish this accepted-and-deleted message from a never-accepted send. Reusing the same UUID alone does not prevent republication after its record has been forgotten.

**Suggested correction:** distinguish receipt/media retention from durable accepted-ID deduplication. Specify what create, complete, and lookup return for an accepted ID whose inbox entries are gone. A durable tombstone or equivalent accepted-ID record can preserve the no-second-delivery rule, but the client also needs a defined terminal outcome. Test this sequence across server restart. Do not invent a shorter client retry deadline to avoid the problem; the contract explicitly has none.

### R4 — High: inbox cards require presentation data that the accepted inbox wire does not supply

**Evidence:** [Profile card rules](../../product/communication-contracts/user-profile.md#2-decided-product-meaning), lines 42–47; [inbox snapshot fields](../../product/communication-contracts/inbox-and-media.md#2-inbox-snapshot--get-v2inbox-accepted-route), lines 86–100; [map scope](implementation.md), lines 9–11 and 47.

Core cards must use the sender's current `card_background_id`; fallback applies when that ID is missing or unknown. The inbox summary supplies `sender_user_id` and `sender_name`, but no avatar/background projection, and explicitly omits `profile`. The map excludes profile editing, and the proposed `/v2/me/profile` route would only describe the acting user, not every sender. A cached sign-in roster is not a documented solution for refreshing presentation throughout a signed-in session or for senders no longer in the roster.

Thus the implementation has no agreed data path for a known, non-default sender card background. Always falling back would not satisfy the current-background rule.

**Suggested correction:** include optional sender presentation fields in the inbox summary or define another accepted read path and refresh policy. Define whether sender-presentation changes advance the inbox revision or are applied independently of membership revision. Keep profile editing and `profile_accent` out of core card rendering. Test a sender whose background changes while the recipient remains signed in, plus a sender missing from the current hangout roster.

### R5 — Medium: server health freshness depends on an event the server cannot observe

**Evidence:** [Login missed-beat clock](../../product/communication-contracts/endpoint-health-and-login.md#missed-beat-clock-com-open-002-accepted), lines 241–245.

The server owns `last_successful_beat_at`, but a successful beat requires both server acceptance and receipt of a valid acknowledgement by the endpoint. If the server accepts the beat and the response is lost, the server cannot know that the endpoint did not receive it. No acknowledgement-of-acknowledgement is defined.

**Suggested correction:** distinguish server freshness from client operation success: the server clock advances on acceptance of a valid authenticated beat; the client marks its attempt successful only on a valid acknowledgement. Preserve the 180-second server threshold and the rule that stale health never changes the login screen. If end-to-end receipt is intended to govern server freshness, it requires a different explicit exchange. Add a lost-health-response scenario; the existing stale-health scenario should also explicitly say the beats are missed, rather than merely that three periods elapsed.

### R6 — Medium: accepted sketch points do not define how separate strokes replay

**Evidence:** [Delivery sketch bytes](../../product/communication-contracts/message-delivery.md#42-upload-part--put-v2outgoingmessage_idpartskindsequence-accepted-route), line 98; [sketch requirements](../../product/experiences/sketch-record-and-playback.md#6-requirements), lines 172–176.

`flsk2` is exactly `x`, `y`, RGB565, and `t_ms`. It has no pen-up/down or stroke boundary, and no rule saying whether these are independent raster samples or vertices connected by the renderer. Two separate same-color strokes can produce the same point sequence as one continuous stroke sampled across that gap. Connecting every point may add an unwanted line; plotting isolated touch samples may omit intended connecting ink.

This is an encoding/renderer ambiguity, not proof that the selected point format must be replaced.

**Suggested correction:** define the representation explicitly. If points are independently painted raster samples, specify capture interpolation and the matching paint primitive. If they are stroke vertices, define how boundaries are encoded and version any byte-layout change. Add replay vectors for two separated same-color strokes, a single tap, and a fast diagonal. Keep the selected geometry, color rail, and RGB565 decision.

### R7 — Medium: inbox recovery after a rejected refresh has conflicting guards

**Evidence:** [Inbox snapshot rule](../../product/communication-contracts/inbox-and-media.md#2-inbox-snapshot--get-v2inbox-accepted-route), line 55; [failure and continuity](../../product/communication-contracts/inbox-and-media.md#failure-and-continuity), lines 143–144 and scenario `COM-SCN-010` at line 169.

An oversized snapshot must keep the last valid inbox and show connecting. Normal fetches are permitted only when the desk is not in connecting. The recovery schedule is stated only for the case where no valid snapshot remains. A desk retaining an older valid inbox can therefore enter connecting without a clearly authorized recovery fetch. Connectivity-return and successful-refresh triggers appear under the same “not in connecting” guard.

**Suggested correction:** separately define ordinary polling and recovery polling. State which failures enter connecting even with cached membership, what request runs while connecting, and which successful response clears that condition. Define equal-revision success as a possible readiness result without unnecessarily replacing membership. Test: valid revision 40, oversized response, then a valid response while Wi-Fi never disconnects. Preserve cached selection and no-autoplay behavior.

### R8 — Medium: map gate status still describes accepted choices as unresolved

**Evidence:** [Map status and gaps](implementation.md#v2-core-journey--implementation-map), lines 3–11 and 35–37; [P1 brief](implementation.md#p1--accept-core-journey-wire), lines 216–221; current login revision 0.12, envelope revision 0.9, inbox revision 0.7, and delivery revision 0.10.

The map still says routes, token format, codecs, chunking, HTTP status numbers, and snapshot bounds await acceptance. Current contracts accept these choices, including the 32-byte token, refresh route, single 262144-byte inbox body, PCM audio, `flsk2`, and 16384-byte parts. Its session workstream still calls expiry and refresh follow-on. This can reopen settled decisions or block work for the wrong reason.

However, acceptance of the decisions does not demonstrate completion of all P1 deliverables: P1 also requires a compatible fixture, manifest, and tests. The inspected server tree contains lab fixtures; the LAB-02 server's `fl.inbox-page/2` name is explicitly a lab subset, not evidence of a complete current-contract fixture.

**Suggested correction:** record the exact accepted contract revisions and separate decision acceptance from fixture delivery/verification and implementation authorization. Retitle or narrow P1's remaining work accordingly. Refresh stale “proposal/open” language in active explanatory sections, while leaving historical revision records intact. Do not mark P1 entirely complete on documentation acceptance alone.

### R9 — Medium: the package table and canonical sequence disagree on P8's prerequisites

**Evidence:** [Package table](implementation.md#orchestration-packages), line 208; [canonical sequence](implementation.md#suggested-implementation-order), line 352; P8 deliverables and verifier, lines 269 and 332–334.

The table gives P8 dependencies P1, P2, P5, and P7. The canonical sequence additionally requires P6. P8 must return to the previous inbox selection and its verifier watches P6 selection behavior. An orchestrator following the table can assign P8 before the required inbox integration exists.

**Suggested correction:** add P6 to P8's dependency list, or explicitly separate an independently verifiable delivery engine from its inbox handoff. Also clarify P4's completion boundary: its verifier currently refers to all login clusters even though credential fencing belongs to the later P5 package. Package completion should not require behavior assigned only to a future package.

## Smaller corrections

- The [delivery complete example](../../product/communication-contracts/message-delivery.md#43-complete--post-v2outgoingmessage_idcomplete-accepted-route), line 110, says 96000 audio bytes, three parts, and 8000 ms. At 16 kHz mono signed 16-bit PCM, 96000 bytes is 3000 ms and needs six 16384-byte parts. For 8000 ms, use 256000 bytes and sixteen parts. Even illustrative examples should pass the accepted validators.
- The [inbox hash-failure scenario](../../product/communication-contracts/inbox-and-media.md#failure-and-continuity), line 163, says “Do not play,” while prefix playback permits audio before the full hash is known. Clarify that a late hash mismatch pauses and fails the remaining playback; it cannot undo already played audio.
- The map describes Level 1 updates for “badges,” but carousel `EXP-040` explicitly excludes unread state. Name the actual supported card updates so this wording does not introduce an unread badge.
- Sketch `OPEN-SKP-01` and `OPEN-SKP-03` now record accepted wire, but older prose in that experience and `SCR-RECORD-SKETCH` still calls the packing open. Remove the obsolete active wording without changing the accepted format.

## Decisions that this review does not reopen

- Core scope remains login, inbox/playback, record/send, and Volume. Profile editing and the settings hub remain excluded.
- Card faces use current `card_background_id`, never `profile_accent`; initials and `card-bg-01` remain the defined fallbacks.
- Finished-send priority and suspension of inbox fetching are accepted behavior, not optional performance optimizations.
- An expired or lost session does not automatically send the person to PIN or the roster. The login spec explicitly requires mute and PIN sign-in for a replacement credential. The resulting potentially indefinite connecting state should be tested as specified, not silently “fixed” by automatic reauthentication.
- Lab feasibility results are not product verification or approval to promote a lab protocol.

## Suggested correction order and validation boundary

Resolve response shapes, duplicate recovery, sender presentation, health-clock observability, sketch replay, and inbox recovery first. Then refresh map traceability, package dependencies, and P1 status against those reconciled contracts. The resulting P1 fixture should exercise these failure sequences, not just ordinary successful requests.

This review inspected the map, active experience requirements and decisions, communication contracts, relevant UI foundations, product bootstrap, and server fixture inventory. No firmware was changed, no device was flashed, and no runtime tests were run. It does not certify the lab evidence inventory or device memory/performance feasibility. The accepted three-minute local PCM capture alone is 5,760,000 bytes; P7/P8 still need an explicit storage allocation plan and target evidence within the existing capture and keep/resume requirements.
