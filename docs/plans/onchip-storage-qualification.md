## At a glance

Prove on one BOX-3 that its unused internal flash can safely hold recordings across writes, renames, resets, and remounts. The experiment uses the tool-validated single-factory layout because it gives the storage island a simple test fixture; it does not decide whether production will use single-factory or dual OTA.

## Background

The X02 + Opus partition study proved that the current 1.5 MiB application slot is too small and mechanically validated two 2.125 MiB layouts. The storage fixture has reached firmware boot on hardware, but the first attempt halted at mount. FAT-over-wear-leveling capacity was observed in the failed retry, while recovery and the complete backend remain unqualified pending the PCM correction experiment.

This experiment isolates that uncertainty before the durable queue is implemented. It uses the validated single-factory fixture only because a factory application is the simplest recovery target for a one-device storage island. The production decision remains open between single-factory and dual OTA; this experiment must not present its fixture as the selected product layout.

No spoken input or attended button action is required. Use deterministic generated PCM tones, generated byte patterns, or existing nonprivate fixtures. Do not commit household recordings, flash backups, credentials, device tokens, or raw NVS contents.

**Related docs:** [`x02-opus-partition-feasibility.md`](x02-opus-partition-feasibility.md), [`phase4-corrections.md`](../evidence/x02-opus-partition/phase4-corrections.md), [`STORAGE.md`](../STORAGE.md), [`durable-outbox-demo.md`](durable-outbox-demo.md), [`MESSAGE-PROTOCOL.md`](../MESSAGE-PROTOCOL.md).

## Experiment boundaries

The experiment may add a numbered island demo, a demo-only partition fixture, a demo-only build configuration, host control scripts, and evidence. It must leave these product inputs unchanged:

- `firmware/v1/`
- `firmware/sdkconfig.defaults`
- any production partition selection or production `partitions.csv`
- X02 behavior and server behavior

Use a separate build directory so an X02 build cannot inherit the experimental partition selection. Do not burn eFuses, enable flash encryption, erase the entire flash, or change boot security. Stop before any destructive step if the flash backup, device identity, port, flash size, or restore command has not been verified.

## Exact experiment fixture

Create a demo-only CSV from the already validated fixture at [`partitions_single_factory.csv`](../evidence/x02-opus-partition/fixtures/partitions_single_factory.csv):

```csv
# Name,   Type, SubType, Offset,  Size, Flags
nvs,      data, nvs,     0x9000,  0x6000,
phy_init, data, phy,     0xf000,  0x1000,
factory,  app,  factory, 0x10000, 0x220000,
outbox,   data, fat,     0x230000,0xDD0000,
```

The fixture targets the detected 16 MiB ESP32-S3 only. Before building, validate the copied CSV with the installed ESP-IDF partition generator and compare the decoded binary table byte-for-byte by field with the source fixture. The build must fail clearly on a flash-size mismatch.

Suggested artifact names are `h32_onchip_storage` for the island demo, `firmware/partitions/h32_onchip_storage.csv` for its partition table, and a dedicated h32 SDK configuration outside `firmware/sdkconfig.defaults`. The implementation may choose equivalent names, but it must record them in the evidence index.

## Phase 1 — Inventory and preserve the device

**Goal.** Identify the connected BOX-3 and establish a tested recovery boundary before changing its partition table.

**Deliverables**

- Enumerate `/dev/cu.usbmodem*` and use the repository device tooling to record the selected port. Reject ambiguous multiple-device selection rather than guessing.
- Record chip model/revision, detected flash manufacturer and size, PSRAM size, USB serial identity where available, current application/build identity, current partition table, and current boot log.
- Read and hash a full 16 MiB flash backup plus a separate NVS-region backup into a private path outside the repository. Never print or commit their contents.
- Decode the backed-up partition table and record a restore command that writes the original bootloader, partition table, application, and required data at their original offsets. Prefer restoring the original complete flash image when safe.
- After preserving the original flash, write a non-secret experiment sentinel into a dedicated NVS namespace using the current demo or a minimal preservation build; record its expected value, preserve all existing namespaces, and save a second NVS-region hash containing the sentinel.
- Verify backups by byte count, SHA-256, and a read-back comparison of at least the partition-table and NVS regions before any experimental flash.

**Acceptance**

- Exactly one target device and port are named, and its detected flash size is 16 MiB.
- The original partition map and firmware identity are recorded.
- Full-flash and NVS backups have verified byte counts and hashes in a non-repository path.
- A concrete restore command has passed a dry-run review against the detected chip, port, offsets, and backup sizes.
- No experimental partition table is written until all preceding checks pass.

**Status:** `verified preservation and restore`

## Phase 2 — Build an isolated storage demo

**Goal.** Produce a reproducible storage-only image that cannot silently alter the X02 build configuration.

**Deliverables**

- Add the exact demo-only partition fixture above and validate it with ESP-IDF v5.4.2 or the repository's pinned version.
- Add an island demo and dedicated build configuration selecting the custom table and 16 MiB flash. Keep `firmware/sdkconfig.defaults` unchanged and use a unique build directory.
- Make the build emit the selected partition CSV path, decoded partition table, application size, binary hashes, and flash command into evidence.
- Add unattended host controls for clean flash, timed serial capture, restart injection, test selection, result extraction, and restore. Tests must start automatically after boot or from a host command; they cannot require speech or button input.

**Host capture timing (orchestrator).** Do not wait hours on a silent port. `scripts/h32_storage_qual.py capture` fails closed with these defaults:

| Check | Sentinel | Experiment |
|-------|----------|------------|
| First serial byte | 45 s | 45 s |
| Milestone | `H32,SENTINEL_READY` by 30 s | `H32,MOUNT` by 240 s (cold format budget) |
| Output stall (after any bytes) | 90 s | 90 s |
| Panic loop | 3× `Guru Meditation` | same |
| Wall-clock cap (`--seconds`) | 30 s default | 5400 s (90 min) default |

Poll progress every **60–120 s** during a healthy experiment (expect `H32,CHUNK` about every 2 s in cadence phases). If a watchdog fires, fix USB/boot/firmware before re-flashing; do not raise `--seconds` to mask a dead capture.
- Generate deterministic payloads on-device or on the host. Include a generated 16 kHz mono PCM tone/pattern and deterministic Opus-sized byte frames; existing nonprivate audio fixtures may be used when their provenance is recorded.
- Ensure the application fits `0x220000` while satisfying the partition study's current 15% headroom policy. Stop if it does not.

**Acceptance**

- ESP-IDF accepts and decodes the built partition table to the four exact rows above.
- The experimental build directory and configuration are distinct from X02, and a before/after diff confirms product defaults and firmware are unchanged.
- The flash command writes only intended experiment regions and does not invoke full-chip erase.
- The demo and host controller can run every non-power-cut case without a person touching or speaking to the device.

**Status:** `build validated`

## Phase 3 — Prove boot, NVS, and filesystem behavior

**Goal.** Show that the partition boots on hardware and exposes stable FAT storage through ESP-IDF wear leveling without damaging preserved NVS state.

**Deliverables**

- Flash the experiment partition table and application using the reviewed procedure, capture the first boot, and prove the running application and partition hashes match the build.
- Read the running partition table and verify `factory` and `outbox` offsets and sizes from the device.
- Verify the NVS sentinel and existing NVS initialization behavior before and after repartitioning. Record whether the chosen flashing command preserves NVS. Do not expose existing values.
- Mount `outbox` with ESP-IDF's FAT-over-wear-leveling API. On a known empty experiment partition, format only when mount reports the expected unformatted condition; distinguish first-format from later mounts.
- Measure first-format time, cold mount time, warm remount time, reported total/free bytes, allocation unit, wear-leveling sector size and configuration, and raw-to-reported capacity overhead.
- Reboot and remount at least five times without formatting. A committed probe file must remain readable and retain its SHA-256.

**Acceptance**

- The device completes a captured boot from the 2.125 MiB factory slot and identifies the expected `0xDD0000` outbox partition.
- The NVS sentinel survives partition-table/application flashing, or the exact reason and required preservation procedure are demonstrated before continuing.
- Formatting is confined to `outbox`; subsequent boots mount without reformatting.
- Measured total/free capacity and overhead are recorded rather than substituted with the earlier `0.92 × 0.92` model.
- Five reboot/remount cycles preserve the committed probe file and checksum.

**Status:** `observed; duplicate probe record correction required`

## Phase 4 — Measure writes and recording rates

**Goal.** Establish filesystem correctness and enough write margin for both compressed recordings and the PCM fallback stress case.

**Deliverables**

- For deterministic 64 KiB and 192 KiB payloads, measure open, sequential write, `fsync`/flush, close, rename, reopen/read, SHA-256 verification, delete, and free-space reclamation. Run at least 20 iterations of each size and report min/median/p95/max.
- Separate write time from flush latency. Report throughput using payload bytes and elapsed monotonic time; identify cache effects and whether data is re-read after remount.
- Verify same-directory atomic rename behavior with `name.part` to final name, replacement behavior where applicable, directory enumeration, and cleanup of an identifiable stale `.part` file.
- Run a real-time Opus-sized cadence for at least 180 seconds using deterministic frames at the selected 16 kbps profile and two-second chunk boundaries. Include manifest-like flush/rename work rather than measuring one bulk file only.
- Run a PCM stress rate of at least 64,000 payload bytes/second for at least 180 seconds. Prefer an additional 256,000 bytes/second margin run if the backend supports it. Use generated tone/pattern data, not a live microphone.
- During cadence tests, record backlog/high-water mark, free space, heap/PSRAM, task stack watermark, missed deadlines, write and flush latency, and final aggregate SHA-256.
- Fill the outbox in bounded steps with validated files while sampling reported free space. Stop short of known metadata exhaustion until Phase 6 defines the reserve.

**Acceptance**

- All final files match their expected SHA-256 after close and after a reboot/remount.
- Rename and delete behavior is documented with no falsely valid final file.
- The 180-second Opus cadence finishes with no missed two-second deadline and no growing backlog.
- The 180-second PCM run sustains more than 64,000 bytes/second including required flushes; any 256,000-byte/second result is reported as measured margin rather than a baseline requirement.
- Capacity, timing distributions, and memory watermarks are present in the committed evidence.

**Status:** `failed PCM cadence`

## Phase 5 — Interrupt and recover writes

**Goal.** Demonstrate that an interruption cannot turn an incomplete temporary write into a valid recording chunk or damage earlier committed chunks.

**Deliverables**

- Add deterministic fault injection that restarts the ESP32 during a `.part` write at controlled offsets: before first sector completion, near half, near final write, after flush, and after rename. Persist only the test case/cycle cursor outside the file under test so runs resume unattended.
- Run at least ten cycles at every interruption point. Use hardware reset through the serial control path or `esp_restart()` and label the reset class accurately. If a controllable power relay is available, repeat the write/flush/rename boundaries with actual power removal; do not describe an EN/software reset as power-loss evidence.
- After every restart, remount without automatic blanket formatting, enumerate final and `.part` files, validate all prior committed SHA-256 values, quarantine or remove identifiable temporary files, and record filesystem diagnostics.
- Include reset after final rename but before test metadata update, reset during delete, and repeated remount after the nearly-full test state.
- Define a fail-safe response for mount failure: preserve the partition for inspection, stop writes, and emit a machine-readable failure. Formatting after an unexpected mount failure is prohibited.

**Acceptance**

- No cycle loses or changes a file committed before the interrupted operation.
- No partial `.part` file is accepted as a final file, and no corrupt final file passes SHA-256 validation.
- Recovery is repeatable for ten cycles at each required reset point, with the exact reset mechanism recorded.
- Unexpected filesystem damage or mount failure stops the experiment and preserves evidence; it is not hidden by auto-format.
- Actual power-loss behavior is either supported by evidence from a named controllable setup or explicitly remains an unproven production risk.

**Status:** `not reached`

## Phase 6 — Set limits and restore the device

**Goal.** Turn measurements into an outbox storage contract and return the device to a known recoverable state.

**Deliverables**

- Derive a conservative free-space floor from the worst measured allocation/metadata behavior, maximum planned atomic file set, and interruption recovery needs. The floor must reserve enough space for the largest chunk, replacement manifest, temporary sibling, filesystem metadata growth, and cleanup/recovery margin.
- Verify the selected floor with a near-full run: refuse a new write before crossing it, retain all previously committed files, remount cleanly, and reclaim expected space after deletion.
- Record the measured usable capacity above the safe floor and translate it into conservative counts for three-minute 16 kbps Opus messages and the tested PCM fallback shape. Keep filesystem measurements distinct from protocol overhead estimates.
- Publish the backend behaviors needed by the durable outbox: mount, format policy, free bytes, open/write/flush/close, same-directory atomic rename, enumerate, checksum, delete, remount recovery, and error reporting. Preserve a backend-neutral interface so removable storage can be qualified later without queue changes.
- Restore the original flash image or original partition table/application using the Phase 1 procedure, reboot, verify the original partition map/application identity, and verify the restored NVS region against the original pre-sentinel backup. If restoring the post-sentinel NVS image instead, verify the sentinel and document that choice. If the next authorized experiment intentionally retains h32, record that state and still prove the restore procedure on read-back artifacts.
- Update [`durable-outbox-demo.md`](durable-outbox-demo.md), [`STORAGE.md`](../STORAGE.md), and the experiment roadmap only with measured results and links to evidence.

**Acceptance**

- The safe floor is a measured, reproducible byte value with a written derivation and a passing near-full test.
- Previously committed files survive refusal at the floor and the subsequent reboot/remount.
- The durable-outbox implementation has an explicit on-chip backend contract and measured limits.
- The original device state is restored and verified, or the retained experimental state and exact restore procedure are recorded for the immediately following authorized experiment.
- Every claim in the result summary is labeled measured, derived, tool-validated, or still unproven.

**Status:** `restore verified; safe floor not reached`

## Stop conditions

Stop the experiment, preserve logs and on-flash state, and do not advance when any of these occurs:

- More than one plausible serial target exists and device identity cannot be resolved automatically.
- The detected chip or flash size differs from ESP32-S3 with 16 MiB flash.
- Backup length/hash/read-back verification fails or a restore command cannot be established.
- Partition generation, decoded offsets, application fit, or flash region bounds differ from the exact fixture.
- A flash step would erase NVS or the whole chip without a separately verified recovery need.
- NVS sentinel or existing NVS initialization unexpectedly changes.
- Mount fails after initial formatting, a committed checksum changes, prior committed data disappears, or the filesystem becomes read-only/corrupt.
- The demo would auto-format after an unexpected mount failure.
- Opus cadence develops backlog or PCM falls below 64,000 bytes/second.
- The host loses serial control needed to identify the current test/reset cycle.
- Restore verification fails.

Record the stopped phase, last successful case, hashes, serial log, and untouched flash regions. A stop result is evidence and must not be worked around by erasing the device.

## Open questions

2. What exact FAT allocation unit and wear-leveling mode does the pinned ESP-IDF choose for this partition? Phase 3 records the actual configuration.
3. Does measured capacity or recovery behavior justify changing the modeled 8% filesystem and 8% safety assumptions?
