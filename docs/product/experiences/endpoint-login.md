Other signed-in behavior is out of scope.

## 2. Scenario and intended experience

The endpoint remains powered continuously. Its physical mute control hides the display and logs out the user when switched on; switching it off wakes the display to sign-in. If Wi-Fi is unavailable, the lower split-pane slot shows a centered `no Wi-Fi` message. If Wi-Fi is available but a valid server response is unavailable, that same lower slot shows `connecting` with three progressive dots. The upper panel and the ⅓/⅔ split stay in place. There is no overlay card and the background does not dim. A 150–200 ms crossfade is used when the lower-slot content changes. Rapid connectivity flaps must not flicker. A valid readiness response is HTTP 200 with valid response information. A person browses user cards for the endpoint's assigned hangout, selects their card, and proceeds to PIN login. The roster is server-owned, with local endpoint login recency used to order familiar users.

The top third of the login layout contains a left-justified “Sign in as ...” message. The bottom two thirds contain a horizontally browsable carousel of touchable user cards. A tapped user card becomes focused and centered where the carousel geometry permits, then opens PIN entry. The carousel centers the focused card, including the first, last, and only card. Hangouts support at least eight users in v2; expansion beyond that is deferred to v3. User IDs are unique and immutable, while user details may change.

## 3. Physical and interaction context

- The physical mute control is a latch. Owner intent is that the endpoint remains powered in both positions.
- Muted: screen off and user signed out. Unmuted: screen on and signed-out login flow begins.
- Login uses touch swipe and tap. The v2 visual constraints are being defined in `docs/product/device-ui/screens`. Accessibility is covered through button sizing and visual/audio feedback; screen-reader and touch-less-display support are not required, English is the only localization language, and no additional color-blind support is required.
- V1 evidence references an ESP32-S3-BOX-3, 320 × 240 touch LCD, and a top-edge mute latch; these are historical device facts, not yet confirmed v2 constraints.
- The owner supplied the shared login layout proportions and heading copy. Card dimensions, art, focus treatment, accessibility, orientation, and localization are OPEN.

Ordinary flow: an unmuted signed-out endpoint checks Wi-Fi and the server. Before the first valid roster, the upper heading is `Loading hangout ...` and the lower slot shows connecting or `no Wi-Fi` as needed. If Wi-Fi is available but server readiness is not, the lower slot shows `connecting` with three dots and retries with a 3-second request timeout, then waits 1, 2, and 4 seconds, then 30 seconds. ## 5. Stage and operation contracts

### Related mute interruption

- Owner-decided behavior: switching mute on while signed in logs out the user, turns off the display, and leaves the endpoint powered. Switching mute off turns on the display and presents the login flow, except that a still-running PIN cooldown is shown instead of selectable cards (`DEC-058`).
- If mute is switched on during PIN verification, cancel sign-in immediately. Ignore all late results from that login operation. Treat the login as canceled, not as a successful authentication. If the server created a session, invalidate it. That cleanup is best-effort and must not block mute or make the person wait (`DEC-056`).
- Exact mute LED, audio, and screen blanking/wake latency are OPEN. If the device boots with mute latched on, it boots powered with the display off. If a PIN cooldown is running when mute is switched on, stay signed out and keep the remaining lockout. Mute does not reset, pause, or extend that 60-second timer. The countdown continues while the display is off. On unmute, show the remaining cooldown if it is still active; if it has expired, use the normal signed-out sign-in flow (`DEC-058`).

### Server readiness and roster refresh

- The server owns the hangout roster. While the endpoint is on and displaying users, it periodically requests the roster to keep its cards synchronized. The owner confirmed that newly received users append to the displayed list and users removed by the server disappear from the cards.
- Unreachable server while signed out replaces the lower split-pane slot with `connecting` and three progressive dots, and retries on the connecting schedule. The upper panel stays. A valid response restores the roster or empty-hangout body in that lower slot.
- If reachability is lost while PIN entry is open, keep the PIN header (`DEC-012`) and replace the keypad with the connection-status panel (`DEC-051`). The person cannot enter more digits until the keypad returns. Entered digits stay. Pause the 60-second partial-PIN idle timeout while that status is showing; resume it when the keypad returns (`DEC-049`). Ignore physical BOOT while the status panel is showing (`DEC-050`). Mute still signs out and turns the display off. If the server later responds that the selected user is unknown, return to the sign-in roster and follow `EXP-036`.
- V1's signed-out hangout probe runs at a fixed 5-second cadence with a 2.5-second request timeout, while the roster and PIN screen are shown; the documented policy shows no exponential backoff. V1's Wi-Fi recovery retry is configured at 30 seconds. The v1 contract has a separate Wi-Fi-unavailable screen. These are v1 reference values, not automatic v2 choices.
- V1 POC heartbeat demos are presence-oriented, not a settled endpoint-health policy: h20 reports mute-latch availability and receives peer online/availability; h24 can batch device logs on each heartbeat. A server-twin smoke demo posts every 2 seconds, but that demo cadence is not a production device requirement. No general v2 heartbeat interval is established by those demos.
- V2 readiness requires HTTP 200 with valid response information. Wi-Fi unavailable shows `no Wi-Fi` in the lower slot. Malformed or unclassified server errors show `connecting` in the lower slot. Response-field validation remains OPEN in the [communication contract](../communication-contracts/endpoint-health-and-login.md).
- **Owner-decided roster refresh policy:** when the roster is active, refresh every 60 seconds. If there has been no user activity and no roster change for 10 minutes, slow refreshes to every 5 minutes. Return to 60-second refreshes after user activity or a roster change. On unmute, check connectivity before showing selectable cards. A single failed periodic check gets one immediate retry; if that retry fails, replace the roster body with connecting. Normal roster polling uses a one-second request timeout (`DEC-038`). Connecting attempts that use the same roster/readiness request use a 3-second request timeout (`DEC-044`). That 3 seconds is the request timeout, not a second timer around the 1-second poll. Response validation and failure taxonomy are proposed in the [communication contract](../communication-contracts/endpoint-health-and-login.md).
- When Wi-Fi returns, change the lower-slot copy to `connecting` if a valid response is not yet available, reset the connecting backoff, and attempt the server immediately with the 3-second connecting request timeout. After a failed connecting attempt, wait 1 second, then 2 seconds, then 4 seconds, then 30 seconds, and stay at 30 seconds thereafter (`DEC-042`). A later successful connection resets that backoff. Response fields, validation rules, freshness window, and protocol details for “valid response information” are proposed in the [communication contract](../communication-contracts/endpoint-health-and-login.md). Make the one immediate retry after a transient periodic-check failure before replacing the roster body. That roster-side retry still uses the one-second poll timeout. The 3-second connecting request timeout and 1/2/4/30-second waits apply only after connecting is shown in the lower slot, or on the immediate Wi-Fi-return attempt.
- **Owner-decided endpoint-health heartbeat:** independently of roster requests and user presence, send a health heartbeat every 60 seconds while powered, including while muted, plus on boot and connectivity changes. The server marks the endpoint stale after three missed beats. Stale health is a **server-only** fact: it does not change the endpoint login screen or local login state (`DEC-055`). During an outage, skip and discard failed beats; do not queue or replay them. When connectivity returns, send a **fresh** beat immediately, then resume the 60-second interval. Server stale status clears on a successful beat (`DEC-057`). The heartbeat describes device health, not whether a user is online (`DEC-067`, `EXP-051`): it reports that this powered endpoint is alive, the mute latch, this boot, and why the beat was sent. The server replies with an acknowledgement and server time. It MUST NOT include user names, user presence, peer-online, logs, or any command that could change login. Wire field names and the missed-beat clock proposal remain in the [communication contract](../communication-contracts/endpoint-health-and-login.md). The older v1 POC heartbeat demos are presence-oriented and do not define this policy.
- The assessment recommends that roster polling run off the presentation owner and that poll results not overwrite active user operations. These are engineering constraints, not permission to choose unresolved UI policy.

### Connection status in the lower panel

- Owner-decided presentation (`DEC-051`, `DEC-043`): `connecting` and `no Wi-Fi` replace the lower two-thirds panel content. Keep the existing split-pane layout and the current upper panel. Do not use an overlay card and do not dim the background. Use a **150–200 ms** crossfade when the lower-slot content changes: fade out the current lower content, then fade in the new state. Keep the upper panel stable. Do not slide. Rapid connectivity fluctuations must not produce repeated transitions or flicker (`DEC-060`). Presentation is [`PANEL-STATUS-MESSAGE`](../device-ui/panels/PANEL-STATUS-MESSAGE.md) with [`COMP-STATUS-MESSAGE`](../device-ui/components/COMP-STATUS-MESSAGE.md). The exact anti-flicker hold is delegated to engineering so long as that invariant holds.
- Connecting copy is the word `connecting` with **three** progressive dots beneath it. Wi-Fi copy is `no Wi-Fi`. Neither message has a mailbox icon or any other icon (`DEC-052`). When the condition changes between those two, change the lower-slot copy with the same subtle transition. Restore the previous lower-slot content (roster, empty fill, or keypad) when neither condition remains.
- Physical BOOT is ignored while this status panel occupies the lower slot; it must not return to the roster or clear PIN digits (`DEC-050`). Physical mute still signs out and turns the display off.
- While connecting is showing, each readiness request uses a 3-second timeout (`DEC-044`). After a timed-out or failed request, wait 1 second, then 2 seconds, then 4 seconds, then 30 seconds, and stay at 30 seconds thereafter (`DEC-042`). Continue until a valid response arrives, Wi-Fi becomes unavailable, or mute. A successful connection resets the backoff. Wi-Fi return retries immediately and also resets the backoff. This schedule does not apply to PIN transport retries (`DEC-019`) or to the single immediate 1-second roster retry while cards are still showing.
- Before the first valid roster, including at boot and unmute, the upper heading is **`Loading hangout ...`** and the lower slot shows connecting or `no Wi-Fi` (`DEC-046`, `DEC-048`). After a valid empty roster, the upper heading stays **`Sign in as ...`** and the lower body shows **`No people in this hangout`** (`DEC-062`, `DEC-065`). After a valid non-empty roster, show the sign-in roster.
- If this status appears during PIN entry or verification, keep the PIN header and any entered digits. Replace the keypad in the lower slot. Pause the 60-second partial-PIN idle timeout until the keypad returns. The person cannot tap digits, and BOOT does not change PIN input, until then. Full-canvas PIN cooldown takes presentation priority over this status (`DEC-054`, `EXP-040`).

### Roster and card selection

- Layout: top third, left-justified “Sign in as ...”; bottom two thirds, horizontal user-card carousel.
- Cards are swipeable and tappable. Tapping selects/focuses the card and opens PIN entry. The carousel centers the focused card in the viewport, including when only one user is shown or when the focused user is first or last (outward empty track space is expected).
- Display order: endpoint-local most recent successful login first. Reconcile each server roster against local recency: remove stored IDs absent from the server response, preserve relative recency for retained users, and append server users not yet in local history. If recency cannot be retrieved or applied, use server response order. A server reorder does not override local recency.
- User IDs are unique and immutable; other user profile details may change. Reflect updated details for the same user ID. A malformed roster is not valid readiness and shows connecting in the lower slot (`EXP-024`). Required user identity is `user_id` plus a display name. A missing or unrecognized avatar, or a missing or unrecognized card background, still shows that person (`EXP-054`). Exact field names are proposed in the communication contract.
- If a user disappears from a roster refresh while their PIN screen is open, keep the selected identity and allow PIN submission. If the server responds that the identity is unknown, return to the sign-in roster and immediately request an updated user list. While that refresh is in flight, show `Updating hangout ...` in place of `Sign in as ...` and disable carousel touch; when a non-empty roster arrives, restore `Sign in as ...` and re-enable carousel touch. If that request fails, enter connecting.
- If the focused card is removed while the roster screen is open, focus the nearest remaining card at an earlier index. If the removed card was first, focus the next card. If no users remain, use the empty-hangout state. Reconcile by stable user identity rather than index alone.

### Empty hangout

- Before the first valid roster: same split layout, no cards, heading **`Loading hangout ...`** (`DEC-048`). See [`SCR-EMPTY-HANGOUT`](../device-ui/screens/SCR-EMPTY-HANGOUT.md).
- After a reachable server returns zero users: same split layout, no cards, heading **`Sign in as ...`**, and **`No people in this hangout`** centered in the lower body (`EXP-020`, `DEC-062`, `DEC-065`).
- After a reachable server returns one or more users: show the sign-in roster.
- If server reachability is lost while the empty hangout is showing, keep **`Sign in as ...`** and replace the lower body with connecting.

### PIN login

- Selection freezes the user identity for the PIN operation.
- BOOT behavior depends on PIN progress: with no digits entered, return to user selection; after one to three digits, clear them and remain on PIN entry; after the fourth digit, ignore BOOT while verification is in progress. While the connection-status panel occupies the lower slot, ignore BOOT entirely; it must not navigate or change PIN input (`DEC-050`).
- If one to three PIN digits have been entered and no further digit is entered for 60 seconds, clear the partial PIN and return to user selection. Each entered digit restarts the timeout; this is an endpoint inactivity timeout, not an authentication lockout. Pause that timer while the connection-status panel is showing and resume it when the keypad returns (`DEC-049`).
- **Owner-accepted v1-derived flow:** enter four digits, showing one right-justified masked `*` immediately for each digit; after digit four, temporarily replace the four PIN marks with `checking...` while verification runs asynchronously, and keep the selected user's name and avatar (`DEC-053`); dim and disable the keypad and ignore more taps while checking (`DEC-059`); restore normal keypad appearance and interaction if verification fails; on accepted credentials enter the signed-in message carousel; on wrong PIN restore the PIN marks, clear entry, and briefly replace the selected-user heading with `wrong pin`; a timeout is not a wrong PIN. Five wrong-PIN failures trigger a 60-second cooldown, following v1. The failure counter tracks the currently selected user; switching selected users resets the tracked counter, successful login clears the counter and lock, and cooldown expiry clears the counter. Four total attempts with a 1-second timeout and retry delays of 1, 2, and 4 seconds apply only to a timed-out submission, for about 11 seconds maximum; these transport retries do not count as wrong-PIN failures. If all four transport attempts fail, enter connecting; when connectivity later returns, return to user selection. Malformed or unclassified server errors show connecting. Remaining visual details are tracked in `SCR-PIN-ENTRY`.
- PIN screen geometry, keypad layout, stage transitions (h19 cover-down), and wrong-PIN feedback are delegated to [`SCR-PIN-ENTRY`](../device-ui/screens/SCR-PIN-ENTRY.md). Wrong PIN replaces the identity heading with `wrong pin` for **2 seconds** then clears entry. Cooldown uses two centered lines on [`SCR-PIN-COOLDOWN`](../device-ui/screens/SCR-PIN-COOLDOWN.md) with cover-down entry/exit: `Too many attempts.` then `Try again in <seconds>.` (`DEC-063`). Keep that full-canvas countdown for the entire 60 seconds regardless of connectivity. The timer never pauses or resets because of connection loss. When it reaches zero, return to the split-pane layout and show `no Wi-Fi` or `connecting` in the lower slot only if the issue is still true (`DEC-054`). Mute during cooldown keeps the remaining lockout (`DEC-058`). PIN digit labels are `fl-type-32` and the 3×3 grid must fit entirely inside the 160 px lower slot (`DEC-061`). The 60-second partial-entry timeout and conditional BOOT behavior are decided. Historical v1 timing conflicts: the product brief describes a 2.5-second login timeout while the assessment reports a six-second implementation value; the owner-selected 1-second per-attempt timeout is the v2 decision.
- **Owner-decided duplicate-submit contract:** assign a unique operation key to each PIN submission and reuse it with the exact same request for every retry. A new PIN submission gets a new key. Retain the final result for one minute from the server's first acceptance. For an exact duplicate key during that window, do not reprocess the login; log the duplicate and return the first request's recorded result, including after a lost success response. After that minute, a reused key MUST NOT authenticate and MUST NOT count as wrong PIN (`DEC-068`). A reused key with a different user or PIN MUST NOT create a second login; the endpoint shows connecting, not `wrong pin`. Wire field names remain in the [communication contract](../communication-contracts/endpoint-health-and-login.md).
- If all PIN attempts fail and connectivity later returns, return to user selection and refresh/show the current roster; do not resume the previous PIN entry.
- Pressing mute at either PIN stage cancels login, logically returns to user selection, clears partial PIN state, and turns off the display. Treat that login as canceled. If a server session was created, invalidate it without blocking mute. Unmuting starts the signed-out readiness flow again.
- On server-confirmed authentication, the server issues a session bound to this endpoint and the selected user (`DEC-066`). The login reply does not include the inbox; the signed-in carousel loads inbox separately. Update that user's endpoint-local login recency and enter the signed-in message carousel. Local recency must not advance merely because PIN entry was submitted or because a response is still pending. Later inbox, send, and profile calls use that session. Mute invalidates it (`DEC-056`).
- Any asynchronous result must be bound to the submitted user and current session/operation. Stale or late results must not sign in a different user. This follows SRC-STD-001 and is not a product choice.
- Mute during PIN verification cancels the login operation immediately; its completion cannot restore authentication and must not leave a usable server session.

## 6. Continuity, data, and side effects

- Remote truth: current hangout user membership comes from the server.
- Local truth: successful-login recency is held in memory only for the current boot lifetime; it is not persisted and this feature does not log recency failures.
- Reconcile server membership with endpoint-local in-memory recency: prune local IDs absent from the server, preserve order of retained IDs, and append users without recency history. If no recency is in memory, including after reboot, use server response order.
- User IDs are unique and immutable; user profile details can change and should refresh from server data. New users append; removed users disappear from cards.
- User login is a remote side effect. Each PIN submission has a unique operation key; retries reuse the same key and exact request, and the server replays the final result for duplicate requests during the decided one-minute retention window, which starts when the server first accepts the request (`DEC-068`). A new submission gets a new key. Successful authentication issues a server session bound to this endpoint and user; the login reply does not include inbox content (`DEC-066`). Mute after an in-flight success must invalidate any created server session best-effort (`DEC-056`). The credential dies at the 3-minute bound if that invalidate never arrives (`EXP-055`). After the retention window, or when the same key is reused with different content, do not authenticate and do not count a wrong PIN (`EXP-052`). Wire field names and the invisible invalidate retry count remain in the [communication contract](../communication-contracts/endpoint-health-and-login.md).
- If the physical mute latch is on during boot, boot the endpoint powered with its display off. There is no persistent recency storage or recency-failure logging in this experience.
- Muting signs out per owner input. Local login recency updates only after server-confirmed authentication. Mute during PIN entry or verification clears PIN state and turns off the display.

## 7. Limits and responsiveness

V2 hangouts must support at least eight users; expansion beyond eight is deferred to v3. The roster cadence, connecting 3-second request timeout and 1/2/4/30-second waits, heartbeat schedule, skip-failed-beats recovery, health-beat meaning, session issuance on PIN success, expired and mismatched PIN-key outcomes, lower-slot 150–200 ms crossfade, cooldown presentation priority including mute, keypad dim-while-checking, 32 px PIN digits inside the lower slot, and PIN retry idempotency behavior are decided. Exact wire field names, routes, token format, roster-field validation, cooldown type size, and wake response targets still need definition or measurement before implementation readiness. The anti-flicker hold for rapid connectivity flaps is delegated to engineering. Visual constraints are being defined in `docs/product/device-ui/screens`. Accessibility is covered through button sizing and visual/audio feedback; screen-reader and touch-less-display support are not required. English is the only localization target. No additional color-blind support requirement is specified. The client standard requires bounded input/render work, observable worker outcomes, and operation timeouts.
