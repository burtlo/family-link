## Goal and boundary

Prove that an isolated BOX-3 experiment can play generated long PCM WAV messages with bounded memory, authorization equivalent to the v1 playback context, real byte-range pause/resume/seek, and truthful recovery from transport failures. This is a Phase 2 experiment under [`long-message-experiments.md`](long-message-experiments.md), independent of storage qualification and durable recording.

H36 consists of a dedicated generated-fixture server, isolated firmware/demo, and scripted controller. It must leave product firmware, product server, H34 code/data, and current device state untouched except for the explicitly backed-up experiment image. H36 does not prove H34 can ingest media longer than its present limit, does not prove acoustic intelligibility, and does not authorize X02 integration.

**No implementation, build, flash, or server run starts until H35 evidence is committed and reviewed.** The device restoration and readback gate in this plan is mandatory before the first flash.

## Source-grounded starting points

- `firmware/demos/h18_playback_screen.c`: HTTP WAV playback, RIFF `data` chunk scan, speaker setup, LVGL transport, and bearer header. Its current prefix-discard seek, small single-threaded reads, early read marking, permissive EOF behavior, and use of `ESP_CODEC_DEV_OK` as if it proved all requested bytes were accepted are examples only; do not carry those behaviors forward.
- `demos/server/h18_playback/server.py`: generated-tone/catalog shape, but the existing response materializes the complete short fixture and has no auth or range support.
- `firmware/v1/v1_auth.[ch]`, `firmware/v1/v1_api.[ch]`, and `firmware/v1/v1_types.h`: v1 PIN verification/login request path, bearer plus selected-user request headers, inbox metadata, TLS setup, and API data contracts. Reuse only the necessary isolated interfaces; do not alter these product modules for H36.
- `firmware/v1/v1_carousel.c`: examples of position persistence, read marking, card-exit cancellation, playhead display, and sketch clock callbacks. Its current whole-blob playback path is not suitable for H36.
- `shared/v1/timing.yaml`, generated `firmware/v1/v1_timing.h` and `demos/server/v1_product/web/v1_timing.js`: the shared timing-generation pattern. Current shared timing has no playback buffer, prebuffer, checkpoint, or retry policy; playback-specific values should remain H36-local unless a separate product decision approves a shared contract.
- `demos/server/h34_message_store/server.py`: bounded file response, bearer identity/ACL checks, `206`, `Content-Length`, `Content-Range`, `Accept-Ranges`, stable SHA-256 ETag, and WAV sample-boundary range checks. H34 currently caps messages at 180,000 ms and its range boundary logic assumes a 44-byte WAV header. Preserve H34 unchanged; H36's >180-second fixtures must be served by its own fixture service.
- `demos/server/h34_message_store/qualify.py`: generated 180-second PCM fixture patterns and HTTP range/checksum verification. Its existing 180-second test is not evidence for H36 device playback.
- `firmware/demos/h22_diary.c` and `demos/server/h22_diary/`: chunked capture/upload precedent only; not playback, session auth, or resume implementation.
- Pinned speaker output sources: `firmware/managed_components/espressif__esp_codec_dev/platform/audio_codec_data_i2s.c`, `firmware/managed_components/espressif__esp_codec_dev/esp_codec_dev.c`, and the pinned ESP-IDF 5.4.2 `components/esp_driver_i2s/i2s_common.c` (`i2s_channel_write`, `i2s_channel_disable`). In the newer driver path, the codec layer drops `bytes_written`; during `out_reconfig` it can return OK without an I2S call. The pinned I2S driver can stop a write with a partial prefix and return success when the channel state changes, or return an error after a partial prefix on a queue timeout. The stock 1000 ms wait applies per I2S queue/semaphore wait, not as a whole-call deadline.

These components are reusable references, not completed Phase 2 acceptance evidence.

## Experiment contract

### Fixtures and server

- Generate deterministic, immutable 16 kHz, mono, signed 16-bit PCM WAV fixtures of exactly 180, 240, and 600 seconds. Include a valid RIFF fixture with a non-44-byte header and a `data` chunk whose offset is parsed from RIFF chunks. Record generation parameters, byte length, duration, PCM/WAV SHA-256, and fixture ID in evidence.
- Fixture generation and serving must not require a human recording or private audio. The fixture server serves files from disk in bounded blocks; it must not read whole media into application memory.
- Keep server fixture routes and state isolated from H34 and the v1 product server. Each fixture is immutable for a run and has a stable ETag tied to its content hash.
- Implement and verify full response and byte-range semantics: authorization before metadata/file access; `200` and `206`; exact `Content-Length`, `Content-Range`, `Accept-Ranges`, media type, and ETag. Reject malformed, unsatisfiable, and sample-misaligned ranges. A missing or culled fixture must fail clearly.
- Source-derived limits (HTTP client header/URL capacities, filename/ID lengths, WAV chunk parsing bounds, firmware task stack, and largest allocatable buffer) are **before-build gates**. Record their source and measured values; choose fixture IDs and response metadata to fit verified capacities. Do not silently raise an existing product cap.

### Authentication and message context

The current v1 login flow verifies the PIN through `/v1/session/login`; it does not issue a separate session token. PIN success gates the device client before it initiates playback requests. Each playback request carries the device bearer and selected user's `X-User-Id`; the server enforces bearer validity, selected-user validity, and recipient ACL for metadata and audio. Keep these client and server responsibilities distinct: an invalid PIN proves the client does not initiate protected playback requests, while invalid bearer, invalid/missing selected user, and non-recipient cases prove server denial. Do not describe the PIN as a server-enforced playback session or claim that a separate PIN session token exists. Metadata includes completed recipient-visible fixture context and saved position. Sign-out and selected-user changes invalidate active requests and prevent stale data from being painted or played.

The isolated fixture server/controller may provide a narrow H36-only adapter for generated fixtures, but must document the mapping between its fixture identity/recipient metadata and v1's PIN-gated client plus bearer/user/recipient server checks. Do not claim that H34's device-token authorization alone supplies the v1 client-side PIN gate.

### Device playback and observability

- Use a fixed 32–64 KiB ring buffer. Network receive and speaker delivery run independently so a blocked/stalled network read cannot block LVGL or cause an unbounded buffer. All task, ring, JSON, and RIFF-parser memory must have explicit fixed bounds.
- Start speaker playback only after 250–500 ms of complete PCM is buffered. On underrun, stop advancing sample time, show buffering/recovery state, and resume only after the startup threshold is met again.
- Track output progress from counted I2S-accepted bytes, not `ESP_CODEC_DEV_OK`, requested bytes, received/downloaded bytes, or wall-clock time. Keep the accepted offset aligned to complete 16-bit mono frames. Handle a RIFF data offset other than 44 bytes.
- Parse and validate response status and range metadata before using body bytes. For every resume/seek response, verify the requested byte start against `206`, exact `Content-Range`, expected total length, and ETag. Never resume by downloading/discarding the prefix. Detect changed ETag/fixture identity and cancel or fail visibly.
- EOF is complete only when the expected range/total length and duration are consumed and the counted I2S-accepted output covers the complete expected PCM. Truncated bodies, premature EOF, excess data, malformed headers, mismatched lengths, or missing/partial output acceptance must not set the playhead to duration or mark the message complete. Mark-read remains tied to the first nonzero, frame-aligned accepted I2S prefix; a later truncation does not undo that read event.
- Persist position to isolated server-owned durable state at a 2–5 second checkpoint interval and immediately on pause, card exit, sign-out/user change, mute cancellation, and successful end. Treat a save as acknowledged only after the server has persisted it; position updates are ordered and bound to fixture/message, selected user, and playback generation so stale workers cannot overwrite newer state. Report read/position state accurately on exit. Mark read only after the wrapper reports a nonzero, complete-frame accepted prefix, including when the I2S call returns an error after accepting that prefix; codec status alone never determines read state.
- Keep UI updates incremental and on the UI-safe path. A visible sample playhead and transport state must remain responsive throughout buffering, play, pause, seek, retry, and failure. The scripted controller is the acceptance oracle; no human speaker/listener interaction is required.
- Log fixture/message ID, expected and observed length/hash, HTTP status/range/ETag, received PCM counts, wrapper-observed I2S call count/status/requested bytes/accepted prefix bytes/offsets, playhead/checkpoints, retry count/reason, cancellation generation, ring high-water/low-water, free/largest internal and PSRAM heap, task stack high-water marks, DMA geometry, and buffer capacities. Hash and count only bytes confirmed in the accepted prefix. Logs must reconcile accepted ranges to fixture samples; they do not prove acoustic output.

### Counted I2S output contract

`esp_codec_dev_write()` returns the data-interface status, not an accepted byte count. In the pinned `audio_codec_data_i2s.c`, `bytes_written` from `i2s_channel_write()` is discarded; `out_reconfig` sleeps and returns `ESP_CODEC_DEV_OK` without calling I2S. In pinned ESP-IDF 5.4.2, `i2s_channel_write()` advances `bytes_written` as it copies into DMA descriptors. If the channel stops mid-call, its loop can end with an incomplete prefix and `ESP_OK`; if a queue wait times out, it can return an error after having copied a prefix. Therefore wrapper status and byte count must both be observable.

- Add an H36-demo-only linker wrapper for `i2s_channel_write` (for example, `--wrap=i2s_channel_write`) that calls the real driver and records its returned status, requested length, actual `bytes_written`, and call sequence. Keep the wrapper out of product and other demo links. Bind its records to the sole speaker worker, fixture ID, playback generation, and expected PCM sample/byte offset. Bind the wrapper symbol/options and DMA geometry into the H36 ELF/build manifest.
- Compare each `esp_codec_dev_write()` result with wrapper-call sequence before/after. `ESP_CODEC_DEV_OK` with no I2S call is zero accepted bytes. Accept only the exact reported prefix; hash/count that prefix and retry only the unaccepted suffix. Reject accepted counts greater than requested, inconsistent/multiple calls, offsets outside the active fixture/generation, or counts not aligned to complete 16-bit mono frames. A partial error still records and accounts for the accepted prefix before deciding whether the suffix can be retried or playback must fail.
- Freeze effective output as mono, signed 16-bit, 16 kHz, left-slot mapping through ES8311 hardware volume, with no software-volume conversion, mixing, microphone activation, or I2S/codec reconfiguration from stream start through completion/cancellation. The BSP default is mono 16-bit Philips format at 22.05 kHz; its mono slot macro selects LEFT, but opening the codec at 16 kHz may trigger format/rate reconfiguration. Stage 1 must initialize/establish the exact startup transition and verify the effective runtime slot and PCM-byte mapping before stream start and before counting output as accepted. Do not start position-bearing playback during a reconfiguration window.
- A network reconnect preserves the active speaker/output and DMA channel; it must not close, reopen, or reconfigure I2S. Freeze the pause/resume policy for already-queued DMA frames: preserve and drain them before acknowledging the checkpoint/closing the HTTP stream, and record/measure queue lead. Never discard queued frames and claim sample continuity. Cancellation first inhibits new writes. The sole output owner lets the in-flight wrapper call settle, accounts for its exact accepted prefix, then applies the frozen owner-only close/drain policy. The checkpoint/ack boundary must occur after this policy and must prevent stale-generation writes after acknowledgement.
- The pinned 1000 ms timeout is per wait inside a potentially multi-descriptor write, not a bound on the whole call or cancellation. Stage 1 freezes a source-derived candidate bound and measurement procedure. If H36 proposes a wrapper policy with 50 ms waits, freeze DMA geometry first and derive the maximum waits for the chosen chunk size before build; measure end-to-end cancellation at the relevant device stage. Do not claim a 50 ms overall cancellation bound from a per-wait timeout.

### Recovery and cancellation

Bound retry count and backoff, expose `buffering`, `reconnecting`, and terminal failure distinctly, and permit stop/cancel during every wait. For a live connection drop, reconnect from the exact in-memory successful-speaker sample counter, aligned to a frame; this must neither replay nor skip a sample. Only device/process restart may fall back to the last server-acknowledged durable checkpoint. A replay bound of at most the configured checkpoint interval applies only when checkpoint saves are healthy and persistence acknowledgements are confirmed; failed or stale saves must remain visibly pending/failed and have no guaranteed replay bound. Do not assume unqualified local storage or silently treat an unacknowledged save as durable. A stale worker from an earlier fixture, card, user, or sign-in generation must not write audio, update metadata, or paint UI.

Exercise controlled server restart, connection drop, body truncation, slow/stalled delivery, incorrect range, changed ETag, and fixture removal/cull. Record the expected terminal/recovery state for each injected fault before running it. Do not classify a clean reconnect on a healthy uninterrupted server as forced-interruption evidence.

## Dependency-ordered stages and gates

Each stage is a small, independently reviewable change. A stage is accepted only when its stated implementation, verification, and evidence/commit gate is satisfied. The implementation owner records source revision and evidence before proceeding; a later stage must not mask a failed earlier gate.

### Stage 0 — H35 and device authority gate

**Prerequisite:** H35 hardware-discovery evidence is committed and reviewed.

Before any device operation, privately identify the BOX-3 variant/serial, active image/build identity, partitions, NVS and calibration/user state, USB/serial recovery path, and current boot behavior. Create a private authoritative pre-flash manifest for every hardware epoch with the real device identity, original full-image/NVS hashes, recovery details, and all private backup references. Keep that manifest outside committed evidence and in a locally protected, excluded location. Commit only a sanitized build/mutation manifest and redacted identity binding: source revision, non-secret config hash, app/ELF descriptor and hash, partition table, image offsets and lengths, sector-rounded erase boundaries, experiment image hash, declared runtime NVS/calibration/user mutations, and a non-reversible or otherwise non-identifying device binding. Do not commit device serials, original full-image/NVS hashes, credentials, or private recovery data. Create a complete recoverable backup of the original device state and verify backup hashes/readability against the private manifest. Default to app-only flashing with the original partition table. Require at least 15% free headroom in the app slot after the experiment image; if the artifact does not fit, stop before flash pending a separately reviewed fixture/partition decision. Confirm sufficient RAM/PSRAM and task-stack headroom from H35 plus source/build metadata. Keep product firmware and `firmware/sdkconfig.defaults` unchanged.

**Verification gate:** private authoritative manifest is complete and privately verified; committed sanitized build/mutation manifest and redacted identity binding; independent readback of backup contents and identities; verified offsets, lengths, sector-rounded erase boundaries, 15% app-slot headroom, declared runtime-state mutations, and documented recovery path; no ambiguity in the private record about which device/image is under test. After each hardware epoch, restore and read back the complete original image/state, then boot it and confirm its identity and baseline behavior before committing that epoch's sanitized evidence or advancing. If any part cannot be backed up, restored, or read back, or the image fails the headroom gate, stop before flash.

### Stage 1 — Freeze source contracts and fixture protocol

Read the cited client/server APIs at the chosen source revision. Resolve before any Stage 2 or Stage 3 operation the H36-only route schema, precise PIN client-gate vs bearer/user/recipient server enforcement, auth-to-fixture mapping, 32,768-byte ring, 8,192-byte startup threshold (256 ms at 32,000 PCM bytes/s), 4,096-byte HTTP receive, 1,024-byte speaker request, 4,096-byte maximum RIFF scan plus fixed chunk-count limit, network/speaker task stacks, command-control timeout and cancellation/cleanup candidate bounds, HTTP read/write timeouts, range alignment for arbitrary `data` offsets, ETag/total-length validation, fixture IDs, and device memory/stack headroom. Treat those numeric sizes as Stage 1 candidate choices, not source-proven safety caps, until the exact constraints below are frozen. Freeze mono s16le/16 kHz/left-slot/ES8311 hardware-volume output, no software conversion/mix/mic/reconfiguration during playback, the demo-only linker wrapper and ELF binding, effective sample/slot byte mapping, I2S DMA geometry, queued-frame pause/resume policy, owner/drain/cancel ordering, per-wait timeout policy, maximum derived waits, and source-derived candidate bounds plus a device measurement procedure before any build. Actual cancellation/cleanup timing must be measured and pass the frozen bound at the relevant device stage. Define server-owned durable position persistence, acknowledgement-after-persistence behavior, ordering and message/user/generation binding, and failed/stale save semantics. Define controller commands and fault-injection semantics, including generation IDs that make stale cancellation observable. Capture source references for all inherited caps; leave unknown limits as explicit blockers rather than guessing.

**Verification gate:** reviewed contract document/examples for metadata, client-side invalid-PIN request gating, server-side invalid bearer/user/recipient denials, complete response, range response, non-44-byte header, malformed/changed fixture, durable position ordering/ack/failure semantics, chosen bounded buffer/parser/task sizes, wrapper symbol/build binding, DMA geometry, counted-output and frame-alignment rules, I2S wait derivation, queued-frame pause/resume and queue-lead measurement, owner/drain/cancel ordering, source-derived timing candidates and device measurement procedure, and each injected fault. Actual device timing results are a later stage gate, not a pre-build claim. No separate PIN session token is claimed. No product/H34 contract changes are required or allowed for this stage.

### Stage 2 — Generated fixtures and isolated range server

Implement only the isolated fixture generator/server/controller protocol needed for deterministic fixture selection, auth-context setup, response/range inspection, and server fault controls. This and later stages cannot proceed until Stage 1 has frozen all bounded memory, task, parser, timeout, and cleanup contracts. Generate the 180/240/600-second files plus the non-44-byte-header case. Record fixture hashes and exact media metadata. Keep all run data in an H36-specific location.

**Verification gate:** scripted host checks prove immutable fixture hashes, bounded file streaming, exact full/range bytes and headers, sample-aligned ranges, stable ETags, bearer/user/recipient denial, and deterministic restart/drop/truncate/stall/bad-range/ETag/cull controls. Verify a position-save acknowledgement is issued only after durable persistence and survives isolated-server restart; verify ordered, generation-bound updates and stale-save rejection. The 240- and 600-second cases establish duration beyond H34's 180-second limit without changing or claiming H34 ingestion support.

### Stage 3 — Authenticated device metadata and non-audio UI path

Build the isolated firmware shell that verifies PIN through the v1 login path and gates playback-request initiation on client-side PIN success, carries the device bearer and selected-user identity, fetches completed fixture metadata/position, and provides controller-operated select, play, pause, seek, exit, user-change, sign-out, and mute actions. The server separately enforces bearer, selected-user, and recipient ACLs; login does not create a separate playback session token. Stage 1's fixed resource and timeout/cleanup contracts must be frozen before this device operation. Keep audio delivery disabled in this stage. Protect UI/task interactions with cancellation generations.

**Verification gate:** scripted positive and negative cases pass; invalid PIN prevents the client from initiating metadata/audio requests; invalid endpoint bearer, missing/wrong selected user, and non-recipient requests are denied by the server; no false PIN-session claim is made. Card/user/sign-out changes cancel outstanding requests; playhead and state labels remain responsive under controller actions. Capture memory/stack baseline.

### Stage 4 — Bounded PCM streaming and truthful playhead

Add the fixed ring and independent network/speaker workers. Parse RIFF chunks including the non-44-byte header, prebuffer within the contract, validate response metadata, count wrapper-reported accepted I2S byte prefixes, update the sample playhead only from complete accepted frames, and persist checkpoints after the output owner/drain policy. Add strict EOF and mark-read timing. Do not add recovery fault handling beyond clean pause/range resume until this gate passes.

**Verification gate:** uninterrupted 180/240/600-second playback has full PCM hashes/sample counts equal to the entire expected fixture based on wrapper-counted accepted prefixes; exercise complete writes, partial writes, zero-byte `ESP_CODEC_DEV_OK` during reconfiguration/no-I2S-call, and partial-error returns. Verify accepted prefixes are hashed/counted once and only unaccepted suffixes are retried; reject impossible counts and incomplete frames. Mark-read begins only on a nonzero, complete-frame wrapper-counted prefix, including partial-error calls. Memory use remains bounded across all durations and ring capacity is never exceeded. Verify effective 16 kHz mono left-slot PCM byte mapping before acceptance counts. Non-44-byte WAV plays from the correct data offset. Pause and seek issue real aligned `Range` requests and validate `206`/`Content-Range`/ETag with no prefix discard. For clean pause/resume, verify already-queued DMA frames are preserved/drained before checkpoint acknowledgement and measure/log queue lead; do not discard queued samples and claim continuity. For seek/cancel traces, reconcile explicit accepted sample ranges and checksums against separately generated expected segments so intentional skips are not treated as corruption. Demonstrate UI responsiveness and report heap/stack/ring/DMA metrics. Counted I2S/DMA acceptance is not acoustic evaluation.

### Stage 5 — Exit, identity changes, and bounded recovery

Add card exit, sign-out, user change, and privacy mute cancellation; checkpoint-on-exit; bounded underrun/reconnect/retry/failure state; and generation-safe cleanup. Add controlled server restart, drop, truncation, stall, malformed/bad range, ETag change, and fixture cull scenarios.

**Verification gate:** each scripted case produces its predeclared state, bounded retries, no false completion, and no stale speaker/UI/metadata effects. Exercise complete/partial/zero/no-call/error I2S output; for a live connection drop, accepted sample ranges continue exactly after the last wrapper-counted accepted complete frame, with no replay or skipped sample. For cancel, inhibit new writes, settle and count the in-flight accepted prefix, preserve/drain already-queued frames under the frozen policy, measure/log queue lead, then verify checkpoint acknowledgement and no old-generation output after the boundary. Network reconnect preserves the active I2S/DMA channel. Test device/process restart after healthy, acknowledged checkpoint saves and verify resume from the last server-acknowledged position with replay no greater than the configured 2–5 second interval. Separately fail or stale a save and verify it remains explicitly pending/failed, is never represented as durable, and has no claimed replay bound; do not substitute unqualified local storage. Confirm isolated-server restart preserves every acknowledged checkpoint. Reconcile each trace's explicit accepted sample ranges/checksums against separately generated expected segments; account for intentional seeks and cancellation boundaries. Cancellation must meet the source-derived candidate bound frozen in Stage 1 as measured at this device stage and must not wait forever on blocked reads. Verify controller and UI remain responsive.

### Stage 6 — Soak, evidence, and restore

Run the complete scripted matrix on the backed-up BOX-3, including 600-second playback, repeat pause/seek/exit cycles, and at least one forced interruption per recovery class. Preserve raw controller output, serial logs, server logs, fixture manifest/hashes, source/build IDs, heap/stack/ring measurements, and a concise results summary under an H36-specific evidence directory. Keep raw logs that contain device identifiers or private recovery details in the private excluded location; commit only sanitized/redacted logs and evidence. Do not include family recordings, credentials, device serials, or original full-image/NVS hashes in committed evidence.

**Verification gate:** all Phase 2 criteria below are demonstrated by reproducible evidence, with failed/unsupported cases stated plainly. Restore the exact saved device image/state and perform independent readback plus restored boot verification. Only after restoration is verified may H36 be reported complete. Evidence may support a later separately reviewed X02 integration plan; it does not authorize product edits.

### Per-stage device epoch rule

Any stage that flashes or otherwise changes device firmware is a separate device epoch. Before each epoch, maintain a complete private authoritative manifest with real device identity, original full-image/NVS hashes, and recovery details; do not commit it. Commit only the sanitized source/config/app/ELF descriptor/partition/image-hash manifest with a redacted identity binding, image offsets and lengths, sector-rounded erase boundaries, declared runtime NVS/calibration mutations, and verified 15% app-slot headroom. Exclude device serials, original full-image/NVS hashes, credentials, and private recovery details from commits and shared evidence. Default to app-only flashing with original partitions; if it does not fit, stop before flash pending a separately reviewed fixture/partition decision. Before committing that stage's sanitized evidence or advancing, restore the complete original image and saved device state, independently read back and verify the restoration against the private manifest, and boot the restored image to confirm its identity and baseline behavior. No intermediate experiment firmware may remain on the device between stages. The next stage begins only from that verified restored baseline and repeats its own private manifest and backup/restore/readback/boot gate before its device epoch. Stage 0 defines the authoritative original backup and recovery procedure; every later flashing stage uses that same authority and records its own epoch and sanitized restoration evidence.

## Phase 2 acceptance mapping

| Requirement | Evidence required |
|---|---|
| More than three minutes plays fully with duration-independent memory | Uninterrupted 240- and 600-second runs; full PCM hashes and sample counts equal the entire expected fixture; heap/stack/ring metrics show fixed bounds |
| Pause and range-based resume/seek | Controller trace shows aligned `Range`, `206`, correct `Content-Range`, stable ETag, and no prefix discard; live drop continues exactly after the last wrapper-counted accepted complete frame; seek/cancel/reconnect accepted ranges and checksums reconcile to separately generated expected segments |
| UI remains responsive; position follows counted output | Timestamped scripted UI/state/playhead trace agrees with wrapper-counted, frame-aligned I2S-accepted output bytes, after the defined drain/ack boundary |
| Forced interruption recovers visibly without false completion | Injected drop/restart/truncate/stall traces show bounded retry, visible state, exact in-memory sample continuation on live drop or last server-acknowledged durable checkpoint after process restart (with bounded replay only for healthy acknowledged saves), explicit pending/failed save semantics, and strict EOF handling |
| Authorization protects playback | Client-side invalid-PIN request-gating trace plus server-side bearer, selected-user, and recipient ACL positive/negative traces; no protected metadata/audio on rejected identity |
| Stop/exit and identity changes are safe | Card exit, sign-out, user change, and mute tests show cancellation, final position checkpoint, and no stale work |
| Device is left in its prior state | Backup/readback identity, restoration/readback hashes, and restored boot evidence |

## Explicit limits

- H36 generated-fixture playback does not prove H34 accepts or stores media over 180 seconds. H34 remains unchanged and separately qualified only to its own protocol cap.
- Only wrapper-counted, frame-aligned accepted I2S byte prefixes support the H36 output/sample-count claim; `ESP_CODEC_DEV_OK` alone does not prove acceptance. Counted I2S/DMA acceptance does not prove output was acoustically audible, intelligible, or distortion-free.
- Controller-scripted playback removes reliance on a person listening or pressing controls; it does not replace separate acoustic evaluation if product audio quality is later in scope.
- H36 does not prove Opus/Ogg playback, recording, durable outbox, sketch rendering over the full message, remote-network/TLS deployment, production reliability, or X02 acceptance.
- No acceptance claim may be based solely on h18, h22, H34 host tests, a short smoke run, or a healthy connection without injected faults.
